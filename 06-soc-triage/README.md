# SOC TRIAGE — php2shell

For analysts working alerts generated by `02-detections/`. Written for someone on shift who
has **not** read the dossier.

## The 60-second version

Two memory-safety bugs in **PHP itself** (not in WordPress/Laravel/anything built on it).
An attacker sends crafted multipart requests and can, on vulnerable PHP:

1. get code execution **before your application code runs** (no login, no plugin, no app
   bug), or
2. **leak process memory** — including secrets belonging to *other requests on the same
   worker* — inside a `Set-Cookie: PHPSESSID` response.

Fixed releases: **8.5.12 / 8.4.27 / 8.3.36 / 8.2.35** (2026-10-21). PHP 7.4/8.0/8.1 have
**no official release** — only backports. Patching requires a **worker restart**, not just a
package upgrade.

**Amazon has confirmed in-the-wild exploitation beginning 2026-10-17 — four days before the
public patch.** If you are scoping, start your search there, not at 21 October.

## Which alerts actually matter

Not all of these rules are equal. The ranking below is deliberate — it reflects what we
validated in a lab (see `../05-validation/`), not theoretical severity.

| Severity | Signal | Why |
|---|---|---|
| **P1 — page** | Oversized / non-alphabet `PHPSESSID` **response** cookie (Suricata 2202 6xxxx canaries, `DETECTION-MEMORY-DISCLOSURE.md`) | Direct evidence of **memory disclosure**. Secrets/session tokens may already be stolen. |
| **P1 — page** | `Session object destruction failed` at PHP Request Startup (Sigma) | The **FPM** RCE path. Rare in healthy estates. |
| **P2 — same shift** | NUL byte in `PHPSESSID` request cookie (Suricata **2202610114 / 2202610115**) | An **arm-stage marker published with a working exploit**. Essentially zero legitimate cause. |
| **P2 — same shift** | Giant multipart filename 64 KB+ / 1 MB+ (Suricata **2202610107 / 2202610108**) | Pre-RINIT OOM amplification. |
| **P2 — same shift** | Arm receipt: 500 after giant-filename multipart (Suricata **2202610111**) | Worker survived a failed startup — the precondition for the RCE. |
| **P3 — queue** | Multipart part-header flood / 100+ parts (Suricata **2202610102–0103**, **0109**, Zeek `Multipart_Part_Flood`) | Shapes are real but have legitimate causes (bulk uploaders, form builders). |
| **P3 — queue** | Chunked/close-delimited multipart with no `Content-Length` (**2202610100 / 0101**) | Rare in normal traffic but fires on some legacy clients. |
| **P3 — queue** | Multipart body on non-POST method (**2202610106**) | PHP 8.4+ `request_parse_body` surface. |

**Do not treat a P3 as "nothing".** A P3 from an internet-facing, **unpatched** PHP host
deserves escalation on the *asset's* risk, even if the request shape alone is ambiguous.

## Triage flow

```
Alert fires
   │
   ├─ Is the affected host running a FIXED PHP (8.5.12 / 8.4.27 / 8.3.36 / 8.2.35)?
   │     └─ No / unknown → treat as LIVE RISK. Go to ALERT-TRIAGE.md, then
   │        INCIDENT-RESPONSE.md if any P1/P2 signal is present.
   │
   ├─ Did the workers actually restart since patching?
   │     └─ No → the host is still exposed. Stale worker state survives an upgrade.
   │
   └─ Patched AND restarted → still triage noise, but downgrade severity one level
      and use it to tune source rules.
```

## Things that will bite you

- **A ruleset that fails to load looks healthy.** Confirm Suricata actually loads these rules
  (`suricata -T` exit 0, and alerts appearing in `eve.json`). An earlier package build did
  not load at all. See `../02-detections/DEPLOY-NOTES.md`.
- **TLS termination blind spots.** Suricata sees cleartext only where you terminate or span;
  ModSecurity only where it is in-line. Host-based Sigma/YARA rules catch what network
  sensors miss.
- **`display_errors=Off` is not a get-out.** It blocks one published RCE path; it does not
  stop the disclosure path.
- **EPSS ≈ 6% is not reassurance.** It is a population statistic. On a host an attacker has
  calibrated, the conditional probability is effectively 1.
